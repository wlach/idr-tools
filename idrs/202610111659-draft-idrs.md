# 2026-10-11: Draft IDRs

Owner: Will Lachance <wlach@protonmail.com>

## Overview

<!-- Initial framing inferred from the seeded changes, for discussion. -->

### Problem Statement

Humans and LLMs can try to make an IDR complete too early, before the problem
or solution is fully understood. This makes it harder to use the document to
develop an idea. Finished IDRs can also retain working clutter, making readers
sift through temporary notes and unused template sections to understand the
decisions. We need clear expectations for both drafting and finalization.

### Context (as needed)

An IDR serves two purposes over the course of a change: a working document
while the design and implementation evolve, and a record of the thinking
behind the resulting solution. The template and IDR skill should make that
transition explicit. The human continues to own the design, whether they write
the document themselves or develop it interactively with an LLM.

Implementation and review can change our understanding of what the problem
requires. Keeping the IDR provisional gives us room to record and examine
those discoveries before treating a solution as settled.

### Goals

- Make it easy to start with questions, tentative explanations, and incomplete sections.
- Keep the IDR useful as implementation changes our understanding.
- Leave a readable record of the motivation, chosen approach, and relevant future possibilities.
- Give humans and LLMs consistent expectations for drafting and finalizing an IDR.
- Provide a mechanical check for signs that an IDR has not been finalized.

### Non-Goals

- Turn IDRs into continuously maintained documentation of the current system.
- Require every template section to be filled in for every change.
- Duplicate routine implementation details already available in the diff.
- Automate finalization or decide whether the design and review are complete.

### Proposed Solution

Create new IDRs with `draft: true` frontmatter and guidance that explicitly
welcomes incomplete thinking. Allow the human to develop the design sections
independently or interactively with an LLM, and revisit the proposed solution
as the work reveals new information.

An IDR remains a draft through implementation and review. Approval of the
proposed solution allows implementation to begin; finalization happens when
the work is ready to merge, meaning any human or LLM review has at least mostly
finished. Keep working notes available while that review can still reshape
the work.

Use a temporary Working notes section for questions, experiments, discoveries,
and implementation details. Before merge, preserve discoveries that explain
the outcome in the relevant durable sections, then remove working notes,
guidance comments, and empty optional sections. The overview should explain
the real-world need and the approach taken; other sections are optional.

Finalization removes the `draft` field rather than setting it to `false`.
If this leaves the frontmatter empty, remove the frontmatter block as well.
Finalization is performed manually. Add an `idr lint` command to check for
remaining signs that an IDR has not been finalized: draft metadata, Markdown
comments (`<!-- ... -->`), or a Working notes section. The command reports
these findings without modifying the document. Passing lint checks these
mechanical conditions; humans still judge whether the record is ready.

## Detailed Design

### Template

Start new IDRs with `draft: true` frontmatter. The opening guidance should
describe the document's lifecycle: a working draft during development and
review, then a historical record of intent and decisions. Explicitly welcome
questions, tentative explanations, and incomplete sections, and encourage
revisiting the document as understanding changes.

Define the finished record around what a reader needs to understand: what
motivated the change, what approach was taken, and what might be done in the
future. Only the overview is required; the other sections are optional.
Technical detail should help explain a decision, with routine implementation
details left to the diff.

Revise the guidance within individual sections:

- **Problem Statement:** allow a half-formed starting point, but require a real-world
  need by finalization. Provide examples that distinguish a problem from a desire
  to build something or adopt a technology.
- **Context and Proposed Solution:** encourage short explanations, ideally under
  200 words each.
- **Goals and Non-Goals:** focus on intended outcomes and scope, leaving
  implementation details to the solution.
- **Detailed Design:** describe architecture where it needs more explanation
  than the proposed solution provides. Module relationships or diagrams can be
  useful; a restatement of code changes is not needed.
- **Optional sections:** explicitly allow deletion when there is nothing useful
  to say. Remove the repeated "(as needed)" suffix from the headings after the
  overview, since the opening guidance establishes their optionality.
- **Working notes (ephemeral):** rename Implementation to Working notes and
  broaden its purpose to include questions, experiments, and discoveries
  throughout the work, alongside implementation details and checklists.

Preserve discoveries that explain why the chosen approach prevailed, including
consequential changes in understanding. The finished record need not recount
every experiment, but should retain the reasoning behind the outcome.

Treat template comments as guidance for the draft stage. Once review is at
least mostly finished, move useful discoveries from "Working notes" into the
relevant durable sections, then remove Working notes, comments, empty optional
sections, and the draft field. Preserve other frontmatter if present, otherwise
remove the entire section.

### Skill and documentation

Update the IDR skill's stages to support the draft lifecycle:

- **Create:** offer independent human drafting or an interactive dialogue with
  an LLM, while preserving human ownership of the design.
- **Implement:** use Working notes for discoveries, implementation results,
  and context for handoff between sessions. Incompleteness alone need not stop
  implementation; a wrong or stale approved design still requires discussion.
- **Verify and revise:** check whether the implementation serves the stated
  intent, as well as whether the diff and IDR agree. A mismatch may call for
  changing the implementation or revisiting the proposed solution. Propose
  updates informed by Working notes, and repeat as human feedback changes the
  solution. Changes to the problem statement, goals, or non-goals require
  human consent.
- **Finalize:** add a separate stage for manual cleanup and linting once human
  or LLM review is at least mostly finished. This may happen in a later session;
  completing implementation does not by itself trigger finalization.

Align the README's examples, terminology, and workflow with the template and
skill, including Working notes, manual finalization, and the lint command.

### Lint command

`idr lint <file>...` checks one or more explicitly named files. It does not
scan the repository by default, so callers can check the current change
without requiring older IDRs to follow the new conventions.

Report findings for each file when its frontmatter contains a `draft` field, contains
Markdown comments (`<!-- ... -->`), or has a Working notes section, including
the template's `## Working notes (ephemeral)` heading. Return a nonzero exit
status if any checked file has a finalization issue; return zero if all checked
files pass. The command does not modify files.

Flag the `draft` field regardless of its value, including `draft: false`:
finalization removes the field while preserving unrelated frontmatter.
Ignore content inside fenced code blocks so examples do not produce findings.

Use stable diagnostic codes inspired by Flake8/Ruff, so each finding identifies
the rule as well as explaining the issue. Proposed codes:

| Code | Meaning |
| --- | --- |
| IDR001 | Draft metadata remains; remove the `draft` field when finalizing |
| IDR002 | Markdown comment remains |
| IDR003 | Working notes section remains |

Include the file path, line number, code, and message in each diagnostic. For
example:

```text
idrs/example.md:2: IDR001 Draft metadata remains; remove the `draft` field when finalizing
```
